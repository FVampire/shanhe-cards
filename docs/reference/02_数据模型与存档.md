# 02｜数据模型与存档

基线：企划v0.3；技术文档v0.1。字段为实现契约草案，允许在建项时补充类型细节，但必须保留语义与不变量。

## 1. 数据的三个层次

| 层次 | 示例 | 存放方式 |
|---|---|---|
| 定义 Definition | 某职业、丹方、行动规则、事件模板 | 版本化内容包，运行时只读 |
| 实例 Entity | 某个人、这一份药材、正在发生的事件 | WorldState，随存档保存 |
| 显示 Projection | 人物卡、未知功法提示、关系入口 | 从实例和玩家知识生成，不作为事实来源 |

定义ID使用稳定字符串，例如`profession.musician`。实例ID与定义ID不可混用。改显示名不改ID，删除定义必须提供迁移或明确拒绝载入旧档。

数字规则：tick为游戏分钟；数量、货币最小单位、经验单位均使用整数。TypeScript实现需验证为安全整数，禁止NaN和Infinity。概率用百万分率`ppm`，范围0—1,000,000；计算乘积也必须处于安全整数范围。原型道行与强度参数上限暂设1,000,000，正式调整上限时重新审查运算。

## 2. 世界根对象

```ts
interface WorldState {
  worldId: string;
  revision: number;
  currentTick: number;
  rulesVersion: string;
  contentVersion: string;
  worldSeed: string;
  entities: Record<string, Entity>;
  projects: Record<string, ActionProject>;
  events: Record<string, EventInstance>;
  facts: Record<string, WorldFact>;
  knowledge: Record<string, KnowledgeRecord>;
  reservations: Record<string, Reservation>;
  schedule: ScheduledTask[];
  rolls: Record<string, RollRecord>;
  receipts: Record<string, SettlementReceipt>;
  commandReceipts: Record<string, CommandReceipt>;
  counters: Record<string, number>;
}
```

数组、Map或索引可以用于运行优化；保存时转换为稳定可序列化结构。派生索引可重建，不作为第二份事实保存。

## 3. 人物

| 字段组 | 必要字段与语义 |
|---|---|
| 身份 | `id`、`name`、`lifecycle`、`location`；lifecycle区分可行动、失能、死亡等状态 |
| 基础属性 | 筋力、身法、体魄、根骨、悟性、神识、心性、气度；变化须有具体来源 |
| 天赋 | `talentIds`与明确的获得记录；天赋钩子只调用允许的效果 |
| 天资 | `aptitudes[domainId]`；影响规则见对应领域，不能直接等同于熟练度 |
| 职业 | `professions[professionId].earnedLevel`及晋升凭据 |
| 技艺 | `skills[skillId].practice`、掌握的方法与专业里程碑 |
| 知识 | 取得文本、理解进展、已掌握方法、疑难与具体心得 |
| 当前状态 | 生命、法力、疲劳、伤势、状态效果等；与寿数分开 |
| 生活与岁月 | `birthTick`、身体年龄进度、慢性问题、延年处理记录、寿数规则ID |
| 意愿 | 个人目标、工作偏好、可接受条件、当前承诺 |
| 组织 | 成员关系ID；任职与权限放在组织关系中 |

**人物不保存可独立修改的`dao`字段。** 展示道行由已获得职业等级求和；判定道行通过专用接口读取。失去职位、暂时无法施展某能力、忘却具体知识不会再次发放旧等级。若未来允许永久损失职业等级，需要单独修订“已获得”的规则。

```ts
interface ProfessionProgress {
  earnedLevel: number;
  advancementReceiptIds: string[];
}

interface InsightRecord {
  id: string;
  subjectId: string;
  sourceEventIds: string[];
  questionKey: string;
  understandingKey: string | null;
  state: 'question' | 'understood' | 'integrated';
  evidenceIds: string[];
}
```

心得描述具体问题与理解，没有可换取任意能力的统一“感悟余额”。一本书、一个知识条目和人物对它的理解是不同对象。

人物地点使用互斥联合：`AtLocation(locationId)`或`Travelling(routeId, from, to, departureTick, arrivalTick)`。在路上的人物不被视为仍在起点。

## 4. 物品、容器与设施

`ItemInstance`包含：`id`、`definitionId`、`quantity`、`quality`、`ownerId`、`containerId`、`location`、耐久及来源记录。

所有权与实际位置分开。置于地面等根层的物品保存location；放入容器或人物携带栏的物品保存containerId，location为空，实际位置沿容器与携带者计算。两种位置来源互斥，不能分别维护互相矛盾的位置副本。

仅定义、品质、绑定状态、来源约束和有效期均相容的物品可合并。唯一法器、书卷和有特殊经历的物品不得因为显示名相同被合并。容器引用不能形成环。

`FacilityInstance`包含：所属者、所在地点、设施标签、工作容量、维护状态、库存入口和允许使用者。丹炉可有一个工作位；同一工作位不能被多个炼制项目独占。

物理书卷被借走后，其他人不能仅凭同一张显示卡继续使用。已经掌握的知识则通过人物知识记录提供条件。

`Reservation`至少包含：`id`、`projectId`、`resourceId`、`mode`、`quantity`、`createdTick`。mode区分人物独占、设施容量、工具独占与库存数量预留。

库存可用量＝当前持有量－有效预留量。预留本身不扣除总量；实际消耗时同时减少持有量和相应预留量。

## 5. 卡牌显示

```ts
interface CardView {
  viewId: string;
  subject: { kind: string; entityId: string };
  displayName: string;
  visibleTags: string[];
  quantityLabel?: string;
  availability: 'ready' | 'busy' | 'remote' | 'unavailable';
}
```

`UiState`记录卡牌位置、分区、缩放、筛选和收藏。整理位置与合并显示不改变库存。开始行动时将viewId解析为实际实体引用，再由内核验证，禁止直接相信UI的可用数量。

## 6. 行动项目

```ts
interface ActionProject {
  id: string;
  definitionId: string;
  boundSlots: Record<string, string[]>;
  state: 'running' | 'awaiting_choice' | 'blocked_system'
       | 'completed' | 'failed' | 'cancelled' | 'interrupted';
  stageIndex: number;
  scheduleGeneration: number;
  startedTick: number;
  dueTick: number | null;
  reservationIds: string[];
  spentResources: ResourceEntry[];
  progressUnits: number;
  rootOccurrenceId: string;
  frozenParameters: Record<string, number | string>;
  settlementReceiptId: string | null;
}
```

候选组合与预览不构成已开始项目。开始成功后才分配项目ID、预留和消费资源。freeze字段仅保存该规则明确要求锁定的参数；地点、人物存活等关键事实仍需在阶段交界重新校验。

`ScheduledTask`至少记录`id`、`dueTick`、`phase`、`stableOrderId`、`sourceId`和`sourceGeneration`。取消或重排项目后递增其调度代数，旧队列项检查不匹配即无副作用跳过；唯一终局凭据继续防止重复完成。

`SettlementReceipt`记录业务键、来源、输入摘要、应用的效果ID和结果。职业晋升使用`characterId/professionId/targetLevel`为唯一业务键，事件结算使用`eventInstanceId`，项目终局使用`projectId`。

## 7. 世界事件、事实与知情

| 对象 | 关键内容 |
|---|---|
| `WorldFact` | 已发生或正在成立的事实、参与者、地点、来源、有效期、修订号 |
| `KnowledgeRecord` | 谁从什么渠道获知哪项事实、可信度、所知细节、传播时间 |
| `EventInstance` | 模板ID、实际参与者、语义发生ID、当前阶段、开始与截止tick、选择状态 |
| `Obligation` | 承诺双方、事项、期限、履行条件、失约后果 |
| `Relationship` | 有向双方、熟悉和信任、共同经历、利益联系、承诺引用 |
| `Reputation` | 主体、观察群体、评价领域、支持该评价的可见经历 |

邪修实施的行为可以生成事实与痕迹，但只有通过目击、调查或传播形成的知识才影响相关人物决策。不能从世界真相直接给所有正道角色加仇恨。

## 8. 宗门与委托

`Organization`保存成员、职位、权限、设施、库存、财务、传承访问规则、对外关系与制度版本。

`Membership`区分成员身份和实际任职；`RoleAssignment`记录授予者、权限范围、生效与撤销时间。权限以组织记录为准，UI选择不能自行授予。

`Delegation`包含：负责人、执行者候选、目标、允许行动、地点、预算、资源上限、异常上报规则、开始与结束条件、制度版本及当前子项目。

管理事务中需要负责人亲自处理的时段同样占用人物主要行动。负责人闭关时只能由已安排的代理处理；不能同时完整承担两项主要工作。

## 9. 随机判定记录

```ts
interface RollRecord {
  key: string;
  kind: 'special_effect' | 'omen' | 'ordinary_check';
  occurrenceId: string;
  subjectId: string;
  probabilityPpm: number;
  sampledPpm: number;
  succeeded: boolean;
  evaluatedTick: number;
  inputsDigest: string;
  randomVersion: string;
}
```

预感发生ID取自真实机会或威胁的语义身份及实质修订号。打开面板、拖拽、切换暂停、命令ID变化不产生新的发生ID。

已经判定的同一预感使用缓存结果，不因人物之后道行变化重抽。新道行对尚未判定的新情境生效。具体效果再次合法施放，则使用已付出成本并记录的施放序号。

## 10. 存档格式

```ts
interface SaveEnvelope {
  saveSchemaVersion: number;
  rulesVersion: string;
  contentVersion: string;
  contentHash: string;
  randomVersion: string;
  slotId: string;
  saveSequence: number;
  worldRevision: number;
  createdAtUtc: string;
  payloadChecksum: string;
  world: WorldState;
  ui: UiSaveState;
}
```

保存tick、项目、预留、队列、随机键、已结算凭据与必要计数器。不要只保存人物面板数值。暂停速度是会话设置，载入后默认暂停。现实创建时间用于显示，不参与游戏结果。

快照是恢复事实来源，领域日志用于追溯和开发期复现；首版不要求用全部历史事件重新构造世界。

## 11. IndexedDB写入与多窗口

建议对象仓库：`slots`存当前有效快照指针与版本；`snapshots`保存版本化快照；`settings`保存非关键偏好。IndexedDB提供结构化数据的事务访问。[API文档](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

保存流程：

1. 在命令或同tick批次完成后取得一致快照。
2. 在数据库事务之外完成序列化、校验和与基本结构验证。
3. 在一次读写事务中检查slot头版本，写入新快照并更新头指针。
4. 事务成功完成后才显示“已保存”；失败则保留旧指针、暂停并提供重试或导出。
5. 成功后保留最近若干快照。清理旧快照不得先于新快照成功写入。

所有保存请求串行合并，旧revision不能覆盖新的存档。关键选择和项目结算后请求保存，另外提供周期保存和手动保存。关闭页时的最后一次写入不作为唯一保障。

同一存档槽只允许一个可写会话。推荐持有以slotId命名的Web Lock，其他标签页只读；数据库头版本检查作为第二层防护。[Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)

缺少所需锁能力时，明确限制为只读已有槽或新建独立槽，不能声称多标签页写入安全。Web端采用HTTPS或本地开发服务运行，建项时验证目标浏览器能力。

浏览器存储可能被用户清理或遇到配额限制。支持持久存储申请，但无论是否获准都提供导出和导入；站点地址变化时依靠导出文件迁移。[存储机制说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## 12. 载入、导出与迁移

载入先暂停，再解析格式、检查版本及内容引用、迁移副本、校验不变量，全部通过后才替换当前世界。失败不覆盖原档，允许导出原文件并返回存档选择界面。

迁移函数逐版本执行，例如`v1ToV2`；必须可测试，不在载入时静默丢弃未知角色、项目或物品。迁移后保存为新快照，旧快照保留。

规则版本变化可能改变概率和事件结算，不能只凭JSON字段兼容就继续运行。旧的RollRecord保留结果，新判定按明确迁移后的规则版本进行；无法安全迁移时拒绝并说明原因。

导出采用包含完整封套的JSON文件；导入验证体积、字段类型、引用、数量和资源约束，不能执行文件内脚本或读取任意路径。校验和用于发现损坏，不作为防作弊认证。
