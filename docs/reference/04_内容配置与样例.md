# 04｜内容配置与样例

基线：企划v0.3；技术文档v0.1。附带[内容样例](examples/内容样例.json)演示一组可相互引用的定义与测试场景，不是已经接入运行内核的游戏内容。

## 1. 配置职责

策划配置“谁能做、需要什么、何时完成、产生什么”；代码负责条件解释、占用、事务、概率和保存。文本修改不应要求修改规则内核。

首版采用JSON和类型校验器，不开放任意JavaScript表达式。正式工程应将本契约实现为运行时校验与构建检查，不能只靠TypeScript类型相信外部文件。

## 2. 内容包结构

| 字段 | 作用 |
|---|---|
| `schemaVersion` | 配置结构版本，当前样例为1 |
| `contentVersion` | 内容发布版本 |
| `status` | 草案或发布状态，样例为`illustrative` |
| `domains`、`skills` | 领域与具体技艺 |
| `professions` | 职业晋升等级、具体条件与能力解锁 |
| `knowledgeDefinitions` | 曲谱、功法、理解主题等知识 |
| `itemDefinitions` | 物品标签、堆叠与使用效果 |
| `workTopics` | 作品或学问成果的主题 |
| `statuses` | 持续状态定义 |
| `locations` | 场景地点，正式工程可拆地图包 |
| `actions` | 行动槽位、条件、时长、占用、结算 |
| `eventDefinitions` | 触发、绑定、选项、期限与结果 |
| `specialEffectProfiles` | 特殊道具效果的生效参数 |
| `omenProfiles` | 祸福预感概率与提示模板 |
| `fixture` | 仅用于样例和测试的初始实例、事实与参与许可 |

所有ID稳定且全包唯一，引用必须存在且属于正确类型。正式发布包不应携带开发测试fixture；样例加载器显式选择是否导入。

fixture人物采用简写，例如`skills`中的数字会展开为SkillProgress，`professions`中的数字会展开为earnedLevel及带来源的初始凭据。测试工厂使用固定的`fixture-defaults-v1`补齐存活、空闲、无伤势、空队列等未填写字段，基础属性与初始身体状态使用显式测试常量。正式存档加载不采用这种缺省补齐，必须经过完整schema与迁移。

## 3. 槽位与占用

行动槽位包含：`name`、`entityKind`、`requiredTags`、`required`、`usage`。`usage`可为`major_actor`、`exclusive_tool`或`reference`。

角色作为实际参与者时使用`major_actor`；纯粹作为讨论话题的某个人物可以是引用。不能把本应参与教学或合奏的NPC标成reference以规避占用。

MVP每个槽只绑定一个实体；同名槽不可重复，默认不同槽不同实体。数量型材料使用单独`costs`描述，不能把一个有十份材料的堆显示为十个唯一工具。

样例中的`costs: []`表示不扣材料或货币，但仍耗时并占用人物与工具。

## 4. 条件语言

条件为带`op`的联合类型，支持`all`、`any`、`not`组合。对未知字段、未知操作或类型不匹配直接报错，不按false静默跳过。

| op | 参数 | 含义 |
|---|---|---|
| `same_location` | `slots` | 所有槽位对象必须在同一实际地点 |
| `skill_at_least` | `actorSlot, skillId, value` | 某项技艺达到指定水平 |
| `knowledge_at_least` | `actorSlot, knowledgeId, stage` | 取得文本、理解或掌握达到相应阶段 |
| `item_knowledge_is` | `itemSlot, knowledgeId` | 所选书卷或谱本确实对应本次学问 |
| `profession_at_least` | `actorSlot, professionId, level` | 指定职业达到要求，无总等级聚合 |
| `has_consent` | `participantSlot, requesterSlot, actionId` | 存在有效参与许可且次数足够 |
| `relation_at_least` | `fromSlot, toSlot, field, value` | 已建立的相关关系满足要求 |
| `has_work` | `actorSlot, topicId` | 人物已有该主题的作品成果 |
| `fact_matches` | `factId, subjectSlot` | 已存在事实属于相关人物 |
| `inventory_at_least` | `ownerSlot, itemDefinitionId, quantity` | 可用库存足够；开始时仍需实际预留 |

知识阶段顺序建议为`acquired < understood < mastered`，它表达理解程度，不替代实际使用熟练度。职业晋升条件中的默认人物槽为`actor`。

普通条件无法读取道行、隐藏的随机抽样值或任意世界路径。已知条件与真实条件使用相同语义，但投影按玩家知情过滤。

## 5. 效果语言

| op | 参数方向 | 语义 |
|---|---|---|
| `gain_practice` | 人物槽、skillId、units | 增加该技艺进展 |
| `change_relationship` | 双方槽、具体field、delta | 改变一条有向关系 |
| `create_work` | 作者槽、topicId、knowledgeId | 生成有作者和来源的作品记录 |
| `record_fact` | factType、主体槽、来源 | 记录可追溯事实 |
| `grant_currency` | 接收者槽、最小货币单位 | 仅用于有资金来源或预留预算的结算 |
| `create_item` | 定义ID、所有者槽、数量 | 生成物品，来源为此次结算 |
| `reveal_fact` | factId、接收者槽、detail | 新增知情记录，不改写事实 |
| `damage` | 目标槽、amount、damageType | 普通伤害，不读取道行 |
| `apply_status` | 目标槽、statusId、durationTicks | 按具体方法施加状态 |
| `resolve_special_effect` | 目标槽、profileId、onSuccess | 调用特殊效果生效判定后应用指定结果 |

职业晋升通过`AdvanceProfession`命令处理，不允许一般事件直接设置等级或增加道行。若事件提供晋升机会，可以记录对应事实，由职业服务验证后完成。

每个效果有稳定`id`。嵌套效果也必须可追溯，编译器检查深度与允许组合。`resolve_special_effect`仅允许在带正确特殊效果标签的道具使用路径中调用，不能把全部普通伤害包进该节点。

普通药物和治疗不配置道行概率。正常的风险检定与两类道行判定是不同resolver，不能共用一个默认“幸运修正”。

## 6. 行动定义契约

必要字段：`id`、`name`、`slots`、`conditions`、`durationTicks`、`costs`、`consentUses`、`onComplete`、`cancelPolicy`、`interruptPolicy`。

占用从槽位usage与实际设施需求生成。`consentUses`规定开始时消耗哪些参与许可次数；许可消耗与资源占用属于同一事务，预览不扣次数。首版参与许可要求预计完成时间早于其expiresTick，开始时再次检查；后续若增加只限制接单时间的合同，必须使用不同字段表达。

`onComplete`示例是确定性结果。后续风险配方可以引用具名的领域resolver，必须同时配置失败结果和解释文本，禁止直接塞入动态公式字符串。

样例采用`release_unspent_keep_spent`取消策略：归还未消费的预留，已消费的时间、许可次数和材料保持已消费。实际收费教学若约定退费，应使用单独经过测试的合同策略。

## 7. 事件契约

样例触发器`work_created`绑定作品作者为`actor`，topicId限定主题。`oncePerActor`使用模板ID与人物ID组成持久业务键，在实例创建时占位，直到终局后保留完成记录。

事件定义`durationTicks`决定从实例创建起的有效期限。每个选项具有`id`、文本、conditions和effects。没有消耗的简短应答可即时完成；演奏、旅行等实际工作应创建后续机会或行动，不能用即时选项绕过耗时与人物占用。

样例邀请选项只记录“愿意进一步商谈”或“婉拒”的事实，不立即支付演出费用。后续合同、演出与付款另行定义，防止把点选邀请等同于完成工作。

## 8. 祸福情境契约

概率profile只有参数与提示模板，不制造世界机会。fixture中的`omenContexts`显式引用已有事实或活动实例，记录主体、接触地点、发生ID、实质修订号和profileId。

正式运行中由事件与旅行模块创建同结构情境。只有人物实际接触时才判定；编辑器把人传送到场景属于测试行为，不代表正式玩家可以隔空获得预感。

`kind`为`good`或`danger`决定提示语义，不改变道行用途分类。未触发预感不会删除原机会或危险；专业调查仍可发现。

## 9. 样例包演示范围

样例包含：

1. 一名学习者与一名愿意合作两次的乐师，处于同一地点。
2. 一把琴和一份谱本，练习时被实际占用。
3. 两次合奏练习各获得6单位音乐进展，学习者从8达到20。
4. 达到条件后可以进行创作，生成作品并引出邀约。
5. 乐修一级需要具体音乐进展、曲谱理解和作品，不要求道行。
6. 一件包含普通伤害与摄魂的测试法器，用于验证只抵抗摄魂部分。
7. 各一个已有危险和求学机会的预感情境。

样例不提供完整战斗系统、收费演出合同或整套寿数规则。它用于让结构与关键边界可检查，完整切片任务见05文档。

## 10. 内容校验分层

| 层次 | 检查项目 |
|---|---|
| 语法 | JSON可解析、无重复键、数值有限且类型正确 |
| 结构 | 必填字段、联合类型、操作白名单、字段拼写 |
| 引用 | ID唯一、引用存在、引用类别正确、槽名已声明 |
| 语义 | 角色占用、消耗非负、时间有效、专业条件有意义 |
| 道行边界 | 无普通条件或效果读取道行，特殊resolver只出现在允许位置 |
| 事件图 | 后续节点存在、有限制的重复触发、无无条件无限零时长循环 |
| 体验 | 音乐链无需战斗加成；结果和文本相符，失败有解释 |

错误应定位到文件和JSON路径，例如`actions[0].conditions[2].knowledgeId`。错误阻止构建；可疑但合法的平衡问题作为警告与审查项。

完整schema、内容编译器与校验测试属于M0任务。此次交付的检查只验证文档及样例能否正确解析、引用与关键约束是否一致，不表示游戏运行行为已经通过测试。
