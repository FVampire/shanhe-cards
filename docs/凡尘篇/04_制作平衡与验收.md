# 凡尘篇｜制作、平衡与验收

版本：设计提案 v0.1。所有数值为初始假设，未经过平衡测试；本次仅新增设计文档。

## 1. 当前实现与目标的差距

依据实际读取的 src/content/game.json、world.ts、model.ts、events.ts、people.ts 及项目说明。历史测试报告是旧版本记录，本次未重新运行或验证游戏测试。

| 当前基础 | 可继续使用 | 必须新增/调整 |
|---|---|---|
| 六个动词、桌面卡牌、拖放与预览 | 主要交互与明确消耗 | 地点、线索、承诺的统一表达与查找 |
| 固定四人、直接使用人物 ID | 身份稳定这一原则 | 按情境生成、角色席位、关系与生命周期 |
| 完整物件在开局发放 | 物品定义与所有权 | 按出身发放，其他通过游戏获得 |
| 音律、学问、药园、调养短流程 | 行动效果与部分内容 | 前后连贯的生活目标与十条事件链 |
| 一项全局合同、一项组织状态 | 预留报酬、委托、异常处理 | 独立合同 ID、多方账本、组织和成员关系 |
| active/willing、有限关系数值 | 当前出场与意愿的局部表达 | 世界/认知/运行精度分离、关系事实、责任保护 |
| 固定离场时限与一次性事件 | 到期结算与日志 | 行程、重逢、持续线索、取消/失败/过期收尾 |
| 年龄、健康、疲劳、一次性延年 | 身体状态分别记录 | 普通照护与初修区分，不用延寿代替首次修行成果 |
| 存档、凭据、唯一占用、确定性随机 | 结算基础 | 人物摘要/档案、引用登记、版本化迁移 |

当前正式 contentVersion 和 rulesVersion 是字面量约束，扩展时同时升级加载、验证和迁移。不得仅向旧 JSON 添加未知字段后声称内容接入完成。

## 2. 经济初稿

新篇章使用“文”作为凡人钱币显示；初期不新增可交易灵石。旧版“灵钱”是单一原型账户，可在迁移后以相同账户余额改显示并给出版本说明，不虚构与未来灵石的兑换率。若将来加入灵石，独立账户和市场。

| 项目 | 初值 | 设计用途 |
|---|---:|---|
| 初始周转钱 | 24 文 | 留出选择和犯错空间 |
| 基础食宿 | 4 文/游戏日 | 2 文饮食+2 文简陋床位，初始干粮抵扣饮食部分 |
| 普通短工 | 6 小时、12 文 | 每周工作三天可付七日基础食宿，并余 8 文 |
| 包食宿帮工 | 6 小时、6 文+当日食宿 | 零现金恢复入口，机会有限但定期更新 |
| 入门专业工作 | 6 小时、毛收入18文、材料约4文 | 净14文，开始体现本领价值 |
| 熟练专业工作 | 6 小时、毛收入24文、材料约6文 | 净18文；实际需求有限，不能无限套现 |
| 基础公开注本 | 12 文 | 数次工作可负担，不设昂贵硬墙 |
| 普通请教 | 依关系可换工或付4—8文 | 体现人情与时间，不能无限免费占用他人 |
| 短途护送 | 12—20 文，预先约定 | 让非战斗路线付得起安全准备 |

核算：普通短工三次收入36文，七日食宿28文；剩余时间可以学习。专业路线收入改善后，玩家可以减少劳动。用两日干粮、初始现金与已付住宿分别结算，不重复收费。

费用只是起点。验证时统计净收入、游戏日投入和现实操作次数；若工作优化使生活完全失去取舍，增加有价值的学习/出行消费，而不是单纯抬高饭钱。

每个支付者有资金来源和需求上限。商人不能原价无限回购玩家刚买的物品；制作收入扣除材料、设施和时间。供货、委托与买卖必须受库存和账本约束。普通 NPC 降级后，未结账户转合同账本，不凭空注销余额。

## 3. 时间与成长

保留游戏分钟作为底层单位，但新内容不要求玩家看着计时器跑完几个月。短时对话、劳动、旅行、长期学习分别安排合理游戏时间，交互节奏独立评估。

- 初期劳动 4—6 游戏小时；基础学习/练习 1—3 小时；城内出行约 10—30 分钟；山路依路段估算。
- 长期工作/练习安排在已验证简单循环后解锁，可预约若干日并设置停止条件。
- 提供“推进到下一项重要结果”，遇到预约风险、资源不足、身体异常、关键来信自动暂停。
- 推进只调用同一调度器，不跳过费用、NPC 行程和到期事件；后台窗口默认不推进，保留原型规则。
- 关键阅读与选择不耗游戏时间；普通期限提前提示，闭关/远行前检查是否冲突。
- 技艺进展依实际练习与难题；重复低难行动收益递减时给出下一项可学内容，不隐藏惩罚。
- 职业升级、方法掌握、寿数变化分别结算，禁止一次晋升自动全领域变强。

不预设主角必须几个月内修成。主流程的 4—6 小时目标靠合理的信息、选择与成果密度实现，试玩中记录等待占比，避免空等。

## 4. 人物生命周期实现顺序

P0：唯一身份、临时人物、持续摘要、角色席位选人、事件收尾和占用释放。

P1：有限联系人、目标与经历记忆、行程、约见、归档、同身份重逢、引用登记。

P2：组织成员职责、固定供货、同行分配、师徒持续关系、多合同账本。

P3：成年亲密关系与共同生活、婚姻责任、家庭、出生、监护、成长、继承。沿用同一身份/事件/责任系统，但需要各自完整玩法，不能只加关系标签就算实现。

每个阶段都必须能保存恢复、结清退出、处理拒绝。不允许先无限生成人物，等后期再补清理。

## 5. 开发里程碑

| 阶段 | 可评审交付 | 完成条件 |
|---|---|---|
| M0 数据与契约 | 人物/事件/合同/归档设计，迁移策略 | 临时角色→持续身份→离场→重逢能够演示，引用不悬空 |
| M1 独自落脚切片 | CH01+CH02+CH03 与简化 CH09/10 | 一条 45—60 分钟路线能从陌生人到初修；无固定熟人硬依赖 |
| M2 不同生活路线 | CH04、CH05、CH06，三种求道渠道 | 至少两条不同专业能够完整通关，作品不依赖战斗奖励 |
| M3 持续人物社会 | CH07、CH08，重逢、通信、同行、24个短事件 | 旧相识的处境产生新事件，所有退场条件结清 |
| M4 完整凡尘篇 | 四条生计、十条事件链、三种方法、完整引导 | 主流程与选支线形成4—6小时初始目标；实际时长实测记录 |
| M5 发布品质 | 表现、可访问性、长档、迁移和性能 | 指定硬件与分辨率上通过质量门槛，缺陷和限制清楚列出 |

以上是依赖顺序，不是日历工期。预算和人员确定前不承诺周数。若制作资源不足，保留 M1 的完整体验，减少其他内容量，不删除失败恢复或人物结算。

## 6. 内容生产与维护

每条事件由策划 ID、文本、角色席位、状态条件、选项、变化、后续与释放策略组成；专业内容用统一行动框架，保留有意义的差异。

内容校验至少检查：ID唯一、引用存在、角色约束有解、条件无直接矛盾、所有选项能收尾、没有重复奖励、费用与所有权明确、期限余量可用、生命周期保护可解除。

生成模板不是每人一份完整手写剧本。模板给来源和合理边界，事件给当前困境，人物状态决定具体选择；作者只在重要节点写不同的结果。

本次清单量：10地点、4生计、3初修方法、12类角色席位、10条多阶段事件链、24个短事件种子、30项行动规格。03中的短事件仍需扩写成正式节点，不能把种子数当成已完成运行内容数。

## 7. 美术、声音与信息设计

- 首批资产：10地点卡、三类人物年龄/职业视觉基础及可组合配件、四类专业工具、食宿物资、方法/线索/承诺/作品图标、天气和阶段反馈。
- 人物视觉生成保存组合参数，重逢不换脸；职业改变可换服饰，年龄改变按阶段演进。
- 姓名、职业标记和关系描述共同帮助辨认，不能只靠颜色；生成姓名避免当前常见联系人重名混淆。
- 地点氛围：集市人声、客舍雨声、作坊工具声、药园风声、山路空旷声。音律作品给可辨识主题，但不要求长曲反复强制播放。
- 人物离开用短消息和去向反馈；后台摘要化不播放“告别”，避免把技术操作演成虚假故事。
- 卡牌展示当前可行动对象，联系人与旧识单独查找；失联者不显示成可直接拖用的现场人物。
- 支持键盘/点击代替拖拽、字体缩放、独立音量、减弱动画、清楚焦点、色觉可辨识状态。重要事件避免连续强制弹窗。
- 首次修持用环境细节变化和清楚说明体现新能力，不能只出现看不懂的属性增长。

## 8. 试玩与平衡验收

首轮邀请 6—8 名未接触项目的试玩者作为问题发现样本，不能据此宣称市场结论。分别测试普通旅人、单熟人背景、低相关天资、自学、拒绝师父、错过招募、全程非战斗等开局。

记录：首次自主行动时间、卡住原因、收入与费用、无操作等待时长、重复劳动次数、认识人数、能记住的人物、主动交往次数、关键选择的解释、初修时间、退出原因。采集范围和用途明示，以本地记录为先。

建议验收问题：

1. 不给口头指导，玩家能否找到食宿与一项工作？
2. 能否说清一个人物是谁、为什么相识、后来去了哪里？
3. 能否通过日志理解一次信任变化和一次失约后果？
4. 稳定生计后是否减少重复操作并留下学习时间？
5. 不求仙时，是否仍愿意完成一件作品或帮助一个人？
6. 拒绝特定人物后能否找到其他有效学习入口？
7. 能否区分普通技艺、修持能力、道行和延寿？
8. 初修失败后是否知道如何调整，而非盲目重试？
9. 人物档案增长时界面是否仍可查找、辨认和联系？
10. 玩家是否觉得离场来自人物自身生活，而非莫名被删除？

## 9. 工程与存档验收

重点场景：事件结算与人物归档同帧；读档重抽；欠款对象离境；借物未还；队友失散；已死角色被席位匹配；同一人同时收到两场邀约；跨日租费与快进；旧版固定人物迁移。

四类自动检查：内容静态校验、生命周期状态迁移、结算幂等与引用完整性、存档恢复一致性。UI检查覆盖新手操作、搜索旧友、预约冲突、释放反馈。仅文案调整无需重复跑全部游戏测试。

压力场景：24/32现场人物、120摘要人物、1000/10000档案；多批事件与一百个结算事务。记录最慢帧、P95查询/存档耗时、存档体积与加载时间，测试硬件同时记录。目标性能预算由首次测量设定，不能沿用旧原型一次数据当作新系统保证。

存档具备版本识别、原档备份、迁移失败回退、档案引用完整性检查。玩家在长时间快进中退出后恢复，所有费用、行程和人物状态必须与正常推进一致。

## 10. 完成定义

凡尘篇完成意味着：玩家独自进入，能以不同方式建立生活；人物相遇有来历、关系有经历、退场有去向；至少一条无需强制战斗胜利的路线到达首次修持与应用；所有路线具备失败恢复；长期运行不无限堆积现场人物；存档和既有人生不被清理策略破坏。

当前交付只完成这些设计规格。游戏中的人物生成器、生命周期、四条完整生计与新增事件尚需按里程碑实现。
